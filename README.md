# Activitatea unui restaurant

Un restaurant are nevoie de un program care sa ii monitorizeze activitatea saptamanala. Prin urmare, programul realizeaza un rezumat al comenzilor restaurantului prin afisarea zilei cu cele mai multe vanzari si numarului total de comenzi din fiecare tip de meniu, atat zilnic cat si saptamanal.

Programul foloseste functii si clase template, reducand duplicarea codului si facilizand usurinta extinderii. De asemenea, programul respecta urmatoarele design pattern-uri: Singleton, Factory si Builder, prin folosirea urmatoarelor clase: ManagerRestaurant, Factory si MasaBuilder, facilizand astfel implementarea clasei SimulareRestaurant.


# Review:

In centrul programului se afla ideea de simulare a activitatii unui restaurant pe parcursul unei saptamani. Activitatea este monitorizata cu ajutorul claselor si a conceptelor de baza a programarii orientate pe obiect. 
Programul incapsuleaza in clasa „Zi” toate mesele de la care s-au facut comenzi de catre clienti in ziua specificata in sirul de caractere „zi”, membra privata a clasei. Unei mese ii este atribuit un vector, „meniuri”, un identificator pentru masa, „id_masa”, si o variabila „timp” care poate avea valori intre 0 si 460, numar ce reprezinta minutul de la deschiderea restaurantului la care s-a inregistrat comanda clientilor. Clasa de baza „Meniu” care impune interfata non-virtuala este mostenita de catre clasa template „MeniuGeneric”, prin intermediul careia se manipuleaza datele despre comenzile clientilor, avand ca date membre un vector care retine numele felului de mancare comandat, pretul acestuia si un atribut de tip „T”, care retine tipul meniului comandat. Pentru a simula functionarea programului, a fost contruita clasa SimulatorRestaurant, care foloseste biblioteca „random” pentru a genera date aleatoare.
Utilizarea clasei template „MeniuGeneric” reduce din duplicarea codului, astfel, cele trei clase („MeniuSpecial”, „PreparatePrincipale”, „Bauturi”) din Tema 2 s-au comprimat in una singura. Pentru a nu modifica mult structura codului din tema precedenta, s-a folosit instructiunea „using”, care ii impune programului sa inlocuiasca declararile claselor derivate din „Meniu” cu instantierea clasei „MeniuGeneric<Tag>” (exemplu: using Bauturi=MeniuGeneric<TagBauturi>). In structurile TagPreparatePrincipale, TagMeniuSpecial, TagBauturi s-a adaugat functia „getnume” apelata prin intermediul datei membe „T tip”, facand posibila afisarea corespunzatoare, ca in varianta precedenta. Un avantaj al folosirii unei clase template este usurinta extinderii codului. Daca s-ar adauga un nou tip de meniu, ar trebui creata o clasa complet noua, chiar daca diferentele fata de celelalte clase sunt minime. In schimb, in varianta actuala este suficienta definirea unui nou tag.  Un alt avantaj al folosirii clasei de tip template este eficienta. Deoarece tipurile sunt rezolvate la compilare, nu exista cost suplimentar de runtime pentru a diferentia meniurile.  Un element important din cadrul clasei „MeniuGeneric” este functia template „afiseaza_nr”, avand ca rol de a afisa numarul de produse existente intr-un anumit meniu. Aceasta utilizeaza datele interne ale obiectului pentru a determina atat denumirea meniului, cat si numarul de elemente comandate.
Un alt context in care s-a folosit template este functia „verificaInterval”, care completeaza clasa „Exceptii” prin adaugarea unei noi restrictii. Aceasta  verifica daca o valoare se afla intr-un anumit interval. Daca elementul este mai mica decat limita inferioara, se arunca exceptia InputInvalid cu mesajul „Valoare prea mica”, iar daca depaseste limita superioara, se arunca mesajul „Valoare prea mare”. In C++, template-urile permit scrierea unui cod generic care poate functiona cu mai multe tipuri de date fara duplicare. In acest caz, functia poate valida atat valori intregi (int), cat si valori reale (float, double) sau orice alt tip care suporta operatorii de comparatie „<” si „>”. 
Programul respecta trei design patterns, si anume Singleton (prin clasa „ManagerRestaurant”), Builder (clasa „MasaBuilder”) si Factory (clasa „Factory”). Singleton este utilizat atunci cand se doreste existenta unei singure instante a unei clase pe parcursul executiei programului.  In cazul de fata, clasa ManagerRestaurant are constructorul privat, si constructorul de copiere impreuna cu operatorul de atribuire sunt sterse, o noua instantiere a unui obiect de acest tip fiind imposibila, accestul facandu-se prin singura instanta disponibila la metoda statica. Clasa reprezinta componenta centrala a aplicatiei si are rolul de a coordona intreaga activitate a sistemului. Ea gestioneaza atat preluarea datelor, cat si interactiunea cu utilizatorul si afisarea rezultatelor. 
Pattern-ul Builder este folosit pentru construirea graduala a unor obiecte complexe si este foarte util atunci cand un obiect necesita mai multi pasi de configurare inainte de a fi utilizat. „MasaBuilder” si „SimulatorRestaurant” demonstreaza utilizarea pattern-ului Builder prin construirea graduala si sigura a obiectelor complexe, crescand lizibilitatea codului si separa logica de configurare si reprezentarea finala a obiectului. Un aspect important al pattern-ului  este faptul ca metodele intorc referinta catre obiectul curent, acest lucru permite apeluri in lant (exemplu: builder.setId(id).setTimp(timp).build(); ). Prin urmare, clasa SimulatorRestaurant nu trebuie sa gestioneze cum se organizeaza memoria interna a unei mese.
Pattern-ul Factory este folosit pentru a ascunde complet complexitatea crearii meniurilor, facand codul mai lizibil, generand diferite tipuri de meniuri. In centrul clasei abstracte „Factory” se afla o ierarhie de clase care o mostenesc, fiecare derivata fiind asignata unui tip de meniu. Rolul lor este vizibil in „SimulatorRestaurant”, unde generarea unui meniu este neimplicata in detaliile produselor, simulatorul creand obiectele prin intermediul indicilor generati random.
Programul respecta principiile SOLID, care au ca rol modelarea unui cod usor de intretinut si extins. „Principiul responsabilitatii unice” impune ca o clasa sa se concentreze pe o singura functionalitate. Prin urmare, „MasaBuilder” are unicul scop de a colecta date si de a construi in siguranta o masa. „Zi” gestioneaza colectia de mese dintr-o singura zi. O-ul din SOLID vide de la „Open-Closed Principle” si se refera la faptul ca ce implementam ar trebui sa fie usor de extins dar mai dificil de schimbat. In program, acest principiu este evidentiat prin clasa „MeniuGeneric”, care permite extinderea usoara a codului. L-ul zice ca subclasele pot inlocui complet clasa de baza fara a afecta corectitudinea programului. Programul functioneaza perfect indiferent de derivata apelata datorita polimorfismului si a interfetei non-virtuale. Urmatorul principiu recomanda utilizarea unor interfete specific care nu au membre nefolositoare. Nicio clasa derivata nu este fortata sa implementeze metode de care nu are nevoie sau care nu ii sunt specifice, reducand redundanta. D-ul din SOLID indica necesitatea folosirii unei interfate. In loc ca restul fluxului de citire sa depinda direct de clasele solide „Bauturi” sau „MeniuSpecial”, programul interactioneaza cu obiecte derivate din functii abstracte. 
In concluzie, programul reprezinta o ilustrare a metodelor specifice programarii orientate pe obiect in C++, demonstrand cum abstractizarea poate simplifica sisteme complexe. Prin polimorfism si flexibilitatea claselor template in MeniuGeneric, codul elimina duplicarea redundanta si maximizeaza eficienta la compilare. Integrarea a celor trei design patterns, Singleton, Builder si Factory, impreun cu respectarea principiilor SOLID, ofera aplicatiei o structura usor de utilizat si extins.
